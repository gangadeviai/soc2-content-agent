# System Description — Marketing Content Writer Agent

Prepared for the SOC 2 Section 3 description (Description Criteria DC 200, 2022 revision). Replace bracketed items.

## 1. Services provided
The Marketing Content Writer Agent ("the Agent") produces first-draft marketing copy (blog posts, landing pages, emails, social posts, press releases) for [Agency]'s clients. Drafts are generated by a large language model from a marketer's brief plus client-specific reference material, then reviewed and approved by a human before publication to the client's CMS.

## 2. Principal service commitments and system requirements
- Client reference material and briefs are not used to train any model and are not retained by the model provider (Zero Data Retention).
- No content is published without approval by a named human reviewer other than the requester.
- Every published piece has a complete, tamper-evident lineage record (who requested, which prompt version, which model, which reference chunks, what was generated, who approved).
- One client's data is never used to generate content for another client.

## 3. Components

### 3.1 Infrastructure
[Cloud provider/region]. Container runtime for the gateway; managed Postgres (drafts) and Postgres+pgvector (knowledge base, read-only role); S3 bucket with Object Lock (COMPLIANCE, 7 years) for audit records; KMS keys with rotation. Egress restricted to the allow-list in `infra/network/egress_allowlist.md`.

### 3.2 Software
FastAPI gateway (`app/`), Anthropic Python SDK pinned to Claude Opus 5.5 (`claude-opus-5-5`), Microsoft Presidio for PII detection, SQLAlchemy. Prompts are versioned files under `prompts/` with manifest hashes.

### 3.3 People
Requesters (marketers), Reviewers (marketing managers; segregation of duties enforced), Administrators (platform security), Engineering (change management via PR), GRC (evidence collection).

### 3.4 Data
| Data class | Examples | Handling |
|---|---|---|
| Client confidential | briefs, unreleased product details, brand guides | redacted before model call; tenant-isolated; retained 180 days |
| Personal data | customer names/emails in case studies | redacted to placeholders; mapping stored inside boundary (encrypted at rest) |
| Generated content | drafts, flags, claims to verify | retained 180 days or until published |
| Audit records | hashes, identities, versions, usage | WORM, 7 years, no raw PII |

### 3.5 Processes
Four stages, each with a human gate:
1. **Brand analysis** – crawl the client's own website within the Git-configured scope → model produces a brand profile → reviewer confirms with the client (`app/brand.py`).
2. **Content strategy** – from the confirmed profile and objectives → pillars + calendar + briefs → reviewer approves (`app/strategy.py`).
3. **Writing** – drafts from approved strategy items (or ad-hoc briefs) → claims to verify + flags (`app/workflow.py`).
4. **Review & publish** – reviewer approves → publish to the brand's WordPress via per-tenant credential → read-back verification (`app/cms.py`).

Change management: PR + CODEOWNER review + CI. Incident response: `INCIDENT_PLAYBOOK_AI.md`.

## 4. AI-specific disclosures (requested by auditors in 2026 engagements)
- **Role:** [Agency] is an *AI user/deployer*; it does not train or fine-tune models. The model provider is a subservice organization (carve-out method) — see `VENDOR_SUBPROCESSOR_ASSESSMENT.md`.
- **Autonomy boundary:** the Agent's runtime identity has no credential capable of publishing, deleting, or writing to the knowledge base. Publishing uses a per-tenant WordPress application password that exists only in the reviewer-triggered publish path. The Agent crawls only the client's own website within a Git-pinned scope.
- **Stage gates:** no strategy without a human-confirmed brand profile; no draft from an unapproved strategy; no publish without a reviewer approval; live content verified against approved content after publish.
- **Model lineage:** model ID pinned in configuration; the served model is logged per request, including when a server-side refusal fallback applies.
- **Human oversight:** mandatory review with verification note; reviewer identity in audit record.
- **Disclosure:** every published piece carries an AI-assistance disclosure line.

## 5. Subservice organizations and complementary controls
| Subservice org | Service | Controls relied upon (CSOCs) |
|---|---|---|
| Anthropic | Model inference | ZDR, no training on API data, SOC 2 Type II, encryption in transit |
| [Cloud provider] | Compute, storage, KMS, Object Lock | Physical security, storage durability, Object Lock enforcement |
| [IdP] | Authentication, MFA | Credential lifecycle, MFA enforcement |

Complementary user-entity controls (CUECs): clients must ensure briefs they submit are authorised for use; client CMS must enforce the publish token's scope.

## 6. Boundaries
In scope: gateway, review portal, drafts DB, knowledge base read path, audit pipeline, prompt repository. Out of scope: client CMS internals, the model provider's infrastructure (carve-out), the IdP.
